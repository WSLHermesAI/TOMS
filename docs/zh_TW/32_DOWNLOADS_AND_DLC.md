# 32 — 下載：共享的測試情境與 DLC 擴充包（規劃）

負責人提出的兩種下載用途（2026-10-21）：
1. **開發者之間共享測試存檔。**開發者把遊戲中的某個時刻存成測試並上傳，其他開發者下載後就能玩或測試同一個時刻。
2. **DLC 擴充包。**不必重新建置就能加入新內容：新武器（道具、玩法設定、美術）、新事件、對話、怪物。

兩者使用同一個下載層（第 3 節），每次下載都用含大小與雜湊值的檔案清單檢查（第 4 節）。目前都還沒有實作。第 7 節列出負責人
需要先決定的事：檔案放在哪裡、誰可以上傳。

## 1. 共享的測試情境

測試存檔就是一個**情境**（[31](31_TEST_SCENARIOS.md)）：一個含 `scenario.json` 與 `save.json` 的資料夾。
`tests/scenarios/` 中的情境已經透過 git 共享。雲端是給開發者**在遊玩中**抓到的時刻用的，不用提交就能立刻分享。

**存下某個時刻：**開發版中的除錯鍵（提案：**F9**）把當下存成一個情境資料夾：
- `save.json`：當下的遊戲進度（存檔格式）；
- `scenario.json`：當下的場景（樓層，或和這個敵人的戰鬥、對話、商店……），加上開發者輸入的 `"_comment"`；
- `shot.png`：一張截圖。

存到 `save/scenarios/<日期>_<名稱>/`。

**分享：**

```
tools\scenarios.cmd upload save/scenarios/2026-10-21_golem_bug    # 上傳到共享儲存空間
tools\scenarios.cmd list                                          # 列出內容（名稱、上傳者、時間、說明）
tools\scenarios.cmd get 2026-10-21_golem_bug                      # 下載到 tests/scenarios/_cloud/（git 忽略）
toms_game --scenario=tests/scenarios/_cloud/2026-10-21_golem_bug  # 開啟它
```

- **上傳是開發者工具，絕不在發佈的遊戲中。**上傳金鑰屬於開發者本人，不放進儲存庫，也不放進任何建置。
- **下載的情境不是測試。**`_cloud/` 中的情境不是 ctest 測試。要讓它成為永久的測試，把資料夾複製到 `tests/scenarios/`
  並提交；之後它就和其他的一樣是 `scenario.<名稱>`。
- **儲存空間保有索引**（`index.json`：名稱、上傳者、日期、遊戲版本、說明），所以 `list` 只需下載一個檔案。
- **舊遊戲版本的情境**仍可載入：存檔會遷移（[28](28_SAVE_SYSTEM.md)）。`list` 會顯示版本。

## 2. DLC 擴充包

**擴充包**只有資料，沒有程式：遊戲資料檔的新條目，加上它們的美術。新武器是一筆 `items.json` 條目、一筆
`weapon_play.json` 條目（玩法設定，[30](30_GAMEPLAY_PLAN.md) 5.6 節）、它的圖示與文字。新事件是一個事件、它的對話、它的
文字。遊戲本來就從資料讀取這些，所以擴充包不需要為每個武器或事件寫新程式。

```
packs/weapon_thunder_spear/
  pack.json
  data/items.json            只有新增的條目
  data/weapon_play.json
  data/text.json
  media/atlas/pack.atlas     擴充包的圖示（含它的頁面 PNG）
```

`pack.json`：

```json
{
  "id": "weapon_thunder_spear",
  "version": 3,
  "minGameVersion": "0.9",
  "name": { "en": "Thunder Spear", "zh_TW": "雷霆之槍" },
  "requires": [],
  "files": { "data/items.json": "sha256:…", "media/atlas/pack.atlas": "sha256:…" }
}
```

**遊戲如何使用擴充包：**

1. **安裝**後的擴充包放在玩家的存檔資料夾：`save/packs/<id>/<version>/`，絕不寫進遊戲本身的 `assets/`。
2. **啟動時**檢查每個已安裝並啟用的擴充包：
   - 每個檔案的雜湊值和 `pack.json` 相符；
   - 遊戲版本至少是 `minGameVersion`；
   - 它 `requires` 的擴充包都在。

   檢查失敗的擴充包會被略過，並告訴玩家原因。
3. **合併：**每個資料檔都是遊戲本身的檔案加上各擴充包的條目。擴充包只能**新增** id。遊戲或其他擴充包已有的 id 是錯誤，
   該擴充包會被略過，除非擴充包把它列在 `"overrides"` 中（是否允許由負責人決定，Q24）。
4. **資源管理器**先在擴充包中找媒體檔，再到遊戲中找。擴充包的圖示有自己的 atlas，所以遊戲的 atlas 永遠不需要重建。
5. **存檔記錄它用到的擴充包**（id 與版本）。缺少擴充包的存檔仍可載入；其中擴充包的道具與事件保留在檔案中，重新安裝
   擴充包後就會回來（[28](28_SAVE_SYSTEM.md)：保留未知欄位）。
6. **發佈前用工具檢查擴充包：**
   - 每個 id 都是新的；
   - 每個圖示都在它的 atlas 中；
   - 每個文字鍵都有六種語言；
   - 武器有 `weapon_play` 條目；
   - 雜湊值都已填入。

   擴充包和遊戲一樣用情境測試（用新武器的測試場）。

## 3. 下載層

兩種用途、所有平台都用同一種下載方式：

```cpp
// C++17，回呼形式（提案）：`done` 在主執行緒執行，`owner` 不在時永遠不會執行
res.fetch("packs/weapon_thunder_spear/3/pack.json", owner, [this](toms::FetchResult r) {
    if (r.ok) readPack(r.bytes); else showError(r.error);
});
```

- **擁有者規則和計時器相同**（[safe_timer.h](../../src/core/engine/safe_timer.h)）：提出下載的畫面已經不在時，下載完成
  也什麼都不做。
- **各平台：**
  - web 使用 `emscripten_fetch`（瀏覽器在背景下載）；
  - 桌面與 Android 在 `job_system` 的工作執行緒上發出 HTTP 請求。

  結果交給主執行緒，GPU 上傳必須在主執行緒進行。
- **穩定性：**提供進度供進度條使用、等待時間遞增的重試、大檔案中斷後續傳，以及使用前第 4 節的大小與雜湊檢查。
- **快取：**磁碟上已有相同雜湊值的檔案不會再下載。
- **`async` / `await`：**之後可以在 `fetch` 之上加一層 C++20 協程（`co_await res.fetch(...)`）。這需要把專案從 C++17 改成
  C++20，是全域的建置變更。回呼版本先完成，不用等它。

## 4. 確認下載正確：檔案清單

每次下載（擴充包、共享情境、遊戲更新）都附有一份**檔案清單**：每個檔案的路徑、大小與 SHA-256 雜湊值。遊戲或工具不信任
任何沒有和清單比對過的東西。

### 4.1 檔案清單

```json
{
  "id": "weapon_thunder_spear",
  "version": 3,
  "created": "2026-10-21T10:00:00Z",
  "total": 1834211,
  "files": [
    { "path": "data/items.json",        "size": 2210,    "sha256": "9f2c…e41a" },
    { "path": "data/weapon_play.json",  "size": 412,     "sha256": "07bd…19c3" },
    { "path": "media/atlas/pack.atlas", "size": 1806,    "sha256": "c1aa…7f02" },
    { "path": "media/atlas/pack.png",   "size": 1829783, "sha256": "5e90…aa61" }
  ]
}
```

- 擴充包的清單就是 `pack.json` 的 `files` 部分（第 2 節）。共享情境有自己的 `files.json`。儲存空間的 `index.json` 記錄
  每份清單本身的大小與雜湊值。
- **為什麼同時用大小與雜湊值：**
  - 大小不用成本就能檢查，能立刻發現中斷或空的下載，也能知道續傳下載到哪裡；
  - 雜湊值發現其他所有問題：壞掉的位元組、伺服器給錯檔案、伺服器上的檔案被改過。

  用 SHA-256 而不是 CRC：CRC 能發現意外，但發現不了被刻意修改的檔案。
- **路徑**使用 `/`，是相對路徑，不含 `..`。清單中的每個路徑都必須唯一。違反這些規則的清單整份拒絕。
- **由工具產生，絕不手寫：**`tools/make_file_list.py <資料夾>` 寫出清單。擴充包檢查工具與 `scenarios.cmd upload` 都會
  執行它，所以清單永遠和上傳的內容一致。

### 4.2 下載單一檔案

1. **下載到 `<名稱>.part`**，絕不直接覆蓋真正的檔案。中斷的下載永遠不會留下遊戲可能讀到的半個檔案。
2. **續傳：**中斷後，如果 `<名稱>.part` 存在且比清單上的大小短，只向伺服器要剩下的部分（HTTP `Range` 請求）。比清單
   大小還長的 `.part` 會被刪除，檔案從頭下載。
3. **大小檢查：**下載結束時，`.part` 必須剛好是清單上的大小。不是的話就重試。
4. **雜湊檢查：**`.part` 的 SHA-256 必須等於清單上的雜湊值。不是的話刪除並重試。雜湊值錯誤的續傳檔案從頭重新下載，
   不再續傳。
5. **放到定位：**把 `<名稱>.part` 改名成 `<名稱>`（同一個磁碟上一次不可分割的改名）。到這時遊戲才能使用它。
6. **重試：**最多 3 次，分別等待 1 秒、4 秒、10 秒。之後該檔案標為失敗，整個擴充包或情境也是。

### 4.3 下載一組檔案（擴充包、情境）

1. **先取得檔案清單。**它很小。用 `index.json`（它的大小與雜湊值）檢查它；販售的擴充包還要檢查簽章（第 5 節）。
2. **和磁碟上的內容比較：**
   - 已存在且大小與雜湊值相同的檔案保留，不下載；
   - 只下載新的或改過的檔案。

   一個 50 MB 擴充包的新版本只改了一個文字檔的話，就只下載那個小檔案。
3. **下載需要的檔案**，一次幾個（最多同時 4 個），每個都依照 4.2。進度顯示已下載的位元組 / 還需要的位元組。
4. **整組完成**的條件是清單中每個檔案都已就位並檢查過。最後寫入一個完成標記（`.complete`，內含清單的雜湊值）。
   - 遊戲只使用有標記且標記和清單相符的擴充包。
   - 沒有標記的一組（下載被中止）下次會繼續完成，不會只用一半。
5. **磁碟上不在清單中的檔案**（舊版本留下的）會在新的一組完成後刪除。

### 4.4 檢查已安裝的內容

- **每次啟動（快速）：**
  - 清單中每個檔案都存在且大小正確；
  - `.complete` 標記和清單相符。

  不計算雜湊值，所以啟動仍然很快。
- **完整檢查**（每個雜湊值）的時機：
  - 快速檢查失敗；
  - 某個檔案載入失敗（壞掉的圖片、無法解析的 JSON）；
  - 玩家對某個擴充包選擇**修復**；
  - 每週在背景做一次。
- **檢查失敗的檔案**會重新下載（依照 4.2）。在那之前該擴充包停用，並告訴玩家是哪個擴充包、為什麼。遊戲永遠不會在擴充包
  只檢查了一半的情況下執行。

### 4.5 上傳（開發者）

`scenarios.cmd upload` 與擴充包上傳的步驟相同：
1. 產生檔案清單，上傳檔案，最後才上傳清單。
2. 把清單讀回來，並用伺服器回報的大小檢查每個已上傳的檔案。
3. 這些都完成後，才把它加進 `index.json`。

上傳中斷的一組永遠不會出現在索引中，所以沒有人會下載它。

### 4.6 測試

- **單元測試**，對本機測試伺服器，不需要網路：
  - 正常下載；
  - 中斷後續傳的下載；
  - 大小錯誤；
  - 雜湊值錯誤，重試後失敗；
  - 含 `..` 或重複路徑的檔案清單；
  - 下載到一半中止、下次執行時完成的一組；
  - 新版本中只改了一個檔案，只下載它；
  - 刪除舊檔案。
- **測試伺服器**可以給錯誤的位元組、太短的檔案，或在中途停止，讓每條失敗路徑都會被執行。
- **`tools/make_file_list.py --check <資料夾>`** 用清單檢查一個資料夾，也會在測試中對範例擴充包執行。

## 5. 安全

- 擴充包**只有資料**。遊戲永遠不執行擴充包中的程式。
- 每個檔案都和 `pack.json` 中的雜湊值比對。賣給玩家的擴充包，`pack.json` 本身要簽章，遊戲內有公鑰。
- 上傳憑證永遠不放在遊戲或儲存庫中。開發者用自己的金鑰透過工具上傳。
- 擴充包不能寫到它的資料夾之外。拒絕含 `..` 的路徑與絕對路徑。

## 6. 工作順序（提案）

| 步驟 | 內容 | 需要 |
|---|---|---|
| 1 | `fetch`（桌面工作執行緒 + web 的 `emscripten_fetch`），由擁有者保護，含進度與重試；檔案清單與它的檢查（第 4 節：`.part`、續傳、大小、雜湊值、整組的 `.complete` 標記）；`tools/make_file_list.py`；對本機測試伺服器的單元測試 | — |
| 2 | 開發版中的 F9「把這個時刻存成情境」 | — |
| 3 | `tools\scenarios.cmd` 的 upload / list / get，連到選定的儲存空間 | Q22、Q23 |
| 4 | 擴充包：`pack.json`、合併資料檔、先從擴充包找媒體、存檔記錄擴充包、擴充包檢查工具、一個範例擴充包（一把武器）與它的測試場情境 | Q24 |
| 5 | 把擴充包交給玩家：遊戲內清單、下載、啟用／停用 | Q25 |
