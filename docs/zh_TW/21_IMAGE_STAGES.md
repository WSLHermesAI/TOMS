# 21 — 以圖片做關卡地圖（設計）

**狀態：** 設計，2026-10-12（負責人的 Q9 提案）。尚未實作。在下方第 3 階段之前，現在的字元地圖照常可用。

## 1. 為什麼

目前每層的地圖是一串字串，每格一個字元。字元的意思由檔案自己的 `legend` 決定（例如
`"1": "monster:bat"`）。這有三個限制：

- **字元不夠用。** 一層能放的不同東西，受限於可用、可打字的字元數。70 層已經用到 149 種不同的東西
  （其中 120 個是事件），單層最多 24 種；每多一種怪物、道具、事件或樓梯，就要再找一個字元。
- **同一個字元在不同樓層意思不同。** `1` 在某層是蝙蝠，在另一層是史萊姆。不讀完每份 legend，
  就無法搜尋「哪些樓層有史萊姆」。
- **不好看懂。** 63 × 42 的字母格很難讀，也很難手動編輯。

負責人的提案：**關卡地圖是一張 2D 圖片。每個像素是一格，像素的值是一個整數 id**，來自一份共用的表。
由解析器把像素讀成關卡。

## 2. 格式

### 2.1 每層一張 PNG

- `assets/data/story/floors/F01.png` 放在 `F01.stage.json` 旁邊（頭目樓層：
  `assets/data/stages/stage01.png`）。
- **圖片大小 = 地圖大小。** F01 是 19 × 16 像素；F70 是 63 × 42。一個像素一格。
- **只用 PNG、RGBA 8 位元，存檔時不帶色彩描述檔。** 失真壓縮（JPEG、失真 WebP）或色彩管理都會改變數值。
- Alpha 必須是 255。其他 alpha 值一律視為錯誤，可以抓到反鋸齒的筆刷痕跡。

### 2.2 像素 → id

```
id = R × 65536 + G × 256 + B        （0 … 16 777 215）
```

共 1670 萬個 id，遠超過遊戲會用到的量，而且每層沒有數量上限。`legend` 不再需要：所有樓層共用同一份 id 表。

### 2.3 id 表：`assets/data/tile_ids.json`

```json
{
  "ids": {
    "0":       "floor",
    "1":       "wall",
    "16":      "door:yellow",   "17": "door:blue",   "18": "door:red",
    "32":      "player_start",
    "48":      "stairs:0",      "49": "stairs:1",     "50": "stairs:2",
    "65536":   "monster:slime", "65537": "monster:bat",
    "131072":  "item:coin",     "131073": "item:gem_atk",
    "196608":  "npc:villager",
    "262144":  "event:ev_village_well", "262145": "event:ev_common_cache_wall"
  }
}
```

| 範圍 | 紅色位元組 | 內容 |
|---|---|---|
| 0 – 65 535 | 0 | 地形與結構：地板、牆、門、起點、樓梯 |
| 65 536 – 131 071 | 1 | 怪物（`monster:<敵人 id>`） |
| 131 072 – 196 607 | 2 | 道具與鑰匙（`item:<id>`） |
| 196 608 – 262 143 | 3 | NPC |
| 262 144 – … | 4 以上 | 事件（`event:<id>`），每個事件池的事件一個 id |

規則：

- **id 永不重新編號、永不重複使用。** 表只會增加。被移除的東西保留它那一列，標記
  `"retired": true`；否則舊圖片的意思會默默改變。
- 紅色位元組表示類別，所以用任何繪圖程式看一眼，就能分辨地形（接近黑）、怪物（暗紅）與事件（較亮的紅）。
- **樓梯**是 `stairs:<n>`：樓層規格裡 `stairs` 清單的第 *n* 項（[05_FLOOR_LINKS](event_editor/05_FLOOR_LINKS.md)）。
  它同時取代現在的 `U` / `D` 與 `stairs_up:<to>` 的 legend 項目。沒有 `stairs` 清單的樓層，
  上樓用 `stairs:0`，下樓用 `stairs:1`。
- **大型怪物**（2 × 1、2 × 2 …）和現在一樣只佔一個像素，也就是牠左上角那格；佔格範圍的其他格是地板。

### 2.4 仍留在 JSON 裡的

不屬於「哪一格放什麼」的資料都留在 `F01.stage.json`：`id`、`name`、`connect`、`footprints`、
`encounter_overrides`，以及樓層規格的 `stairs` 與 `events`。`tiles` 和 `legend` 由一個欄位取代：

```json
{ "id": "F01", "image": "F01.png", "width": 19, "height": 16, ... }
```

`width` / `height` 保留，讓工具可以和圖片大小核對。

## 3. 解析器

- `parseStage`（`src/core/game/core/stage.h`）多一條路徑。JSON 有 `image` 時，用引擎已附的
  `stb_image`（`stb_image_impl.cpp`）解碼 PNG，再把每個像素拿去查 id 表。
- **第 1 階段不改動遊戲其他部分。** 解析器建出和現在相同的 `Stage`：替這層出現的每個不同 id 配一個內部字元，
  再由它們填好 `tiles` + `legend`。移動、繪製、存檔與編輯器的檢查都不必改。單層最多 24 種東西，
  遠低於可用字元數。
- 遇到未知的 id，或 alpha 小於 255，載入會失敗並指出像素位置
  （`F01.png (7, 3): id 65601 is not in tile_ids.json`），而不是默默畫成地板。
- **第 3 階段（之後）：** `Stage` 直接存整數 id，字元就此消失。

## 4. 工具

| 工具 | 變更 |
|---|---|
| `tools/stage_image.py`（新） | 雙向轉換：`F01.stage.json`（tiles + legend）↔ `F01.png` + id 表。會把缺少的 id 加入表中，並確認來回轉換後每格都相同 |
| 關卡編輯器（[19](19_STAGE_EDITOR.md)） | 讀寫 PNG（瀏覽器 canvas 的 `getImageData` / `toBlob`）。調色盤顯示 id 表裡的名稱，不顯示原始數字 |
| 事件索引（`tools/web_editors/floor_index.js`） | 讀取事件像素，讓每層的索引保持正確 |
| 檢視器 | 給人看的除錯配色：每個類別一種易讀的顏色，滑鼠停留時顯示 id，因為存檔裡的顏色是 id，不是美術 |

## 5. 計畫

| 階段 | 工作 | 完成條件 |

## 6. 待負責人決定

1. **用 RGB 打包的 id（本設計）還是索引調色盤 PNG？** 調色盤 PNG 用一般繪圖軟體比較好畫（選第 37 色 = 史萊姆），
   但每張圖最多 256 種值。RGB 打包沒有上限，但要靠關卡編輯器（或除錯配色）才看得出像素代表什麼。
   *建議：* RGB 打包，用關卡編輯器編輯。
2. **每個事件一個 id**（如上；目前 120 個事件，之後更多），**還是幾個「事件欄位」id**，由樓層規格的清單決定是哪個事件？
   每個事件一個 id，圖片就能精確表示哪個事件在哪裡，每層索引也保持精確。*建議：* 每個事件一個 id。
3. 第 3 階段**一次轉換全部 70 層**，還是等每層被編輯時才轉？解析器兩種格式都讀，所以都可行。
   *建議：* 用轉換器一次全部轉換，並以單元測試證明沒有任何改變。
