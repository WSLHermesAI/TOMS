TOMS design map

How the game is put together on 2026-10-31: the frame, the screens and how they switch, the drawing order, events, talking, battle, and how easy each part is to extend. Read from the code (file:line in the doc beside this page).

The layers, top to bottom

Each layer only calls the one below it. The game rules sit in small pure modules with their own tests; one big Game class holds the state and glues the modules, the data and the screens together.

The UI over the battle

Panels, the plays' targets and circles, numbers and banners are RmlUi (view 2), placed in design pixels from the boxes the battle screen reports.

Sprites go in one batch per frame (compute, instancing or CPU path). Meshes, GPU particles and layer pictures sit in the same stream as markers, so the order you draw is the order you see.

Is it extendable?

For content, yes. For new kinds of things, it works but costs more than it should.

easy
New content

Monsters, items, moves, special moves, weapons, events, NPCs, dialogues, floors, missions, texts: a JSON entry, no code.

easy
Rule changes

Numbers live in data; rules live in pure modules with tests, so a change is small and checked.

medium
New kinds

A new event action, play kind, map thing or condition: C++ in 2-3 places (if-chains, no tables).

costly
New screens

A screen is a new flag + its place in three priority lists + a Ui struct + an .rml file + uiEvent names.

What holds it back, with what to do

#Issue (fact)Cost todaySuggested fix
1No screen state machine. ~12 flags; the priority is written in game_session.cpp, buildUiState and draw()a new screen must be added consistently in 3 places; easy to get two screens open a Screen enum + a small stack (push / pop) with one "which screen is on top" function used by input, UI and draw
2Game is one large class (game.h 1,544 lines, ~300 functions, ~350 fields) every feature touches game.h; builds are slow; ownership is unclear move each area's state into its own object (BattleController, DialogueController, MenuController) that Game holds; keep the pure modules as they are
3If-chains instead of tables: uiEvent (32 + 20 names), story actions (3 chains), monster event actions, play kinds (enum + switch)a new verb = edit 2-3 chains; the validator lags (it does not know tryWeapon, chooseWeapon, miniGame)name → handler tables, registered once, which the validator reads too
4Three event systems: map events, monster events (own vocabulary), the event bus (missions only) a monster cannot "run a story action"; things learned once must be learned three times let monster events call the shared story actions; let events listen on the bus
5Content in code: event tile effects matched on the id ("shard", "trap", "cache") a designer cannot add a new tile effectmove them into the events' actions
6Gaps: no eventDone condition; chapter beats not run; old unused data (combat.json, story.json)small confusionsadd the leaf; decide on beats; delete the old files

Fixing 1 and 3 first gives the most: every later screen and every later verb gets cheaper. None of them blocks the current work; they are cleanups to plan, not bugs.
