# 18 — 節點效果，以及格鬥家示範：不用 Spine，動畫編輯器夠用嗎？

擁有者問（2026-10-30）：動畫編輯器能不能取代 Spine？測試方式是：拿一張格鬥遊戲角色模型當參考，用 ComfyUI 畫出角色的各部件，
再用動畫編輯器做出動畫：走路、跑步、攻擊（踢、拳、劍、弓、杖）以及 KOF 式的超必殺連段。擁有者也要求一項 Spine 沒有的功能：
**節點可以掛自訂著色器，作用在這個節點以及它底下的所有子節點**（動態模糊、HDR 繪製）。

本文件記錄：

- 這項功能（§1–4）；
- 使用它的示範（§5）；
- 結論：動畫編輯器做得到而 Spine 做不到的，以及它仍缺少的（§6）。

參考圖是有版權的角色，所以示範角色是**原創設計**。它只沿用參考圖的比例與站姿：大頭、粗壯的前臂與拳頭、寬站姿
（擁有者的選擇，2026-10-30）。

## 1. 效果：子樹先畫成一張圖，再透過著色器畫出

節點的 `fx` 會把**這個節點與它的整個子樹**畫進一張自己的離屏圖，再透過著色器把這張圖畫到下面的內容上。子樹以外的節點不受影響。
效果可以巢狀：一層的圖會畫進包住它的那一層。

| 著色器 | 參數（長度以片段像素計） | 作用 |
|---|---|---|
| `group` | – | 子樹當成一張圖：對下方只有一個透明度（重疊的部件不會互相透出） |
| `motionBlur` | dx, dy, auto, – | 沿 (dx, dy) 拖出模糊。`auto` > 0 時再加上節點自己在最近 1/30 秒的移動量 × `auto` |
| `glow` | 強度, 半徑, 門檻, 光暈 | 顏色 × 強度（> 1 為 HDR：圖是 RGBA16F）。超過門檻的光會溢出輪廓 `半徑` 遠，顏色為 `color` |
| `flash` | 程度 | 朝 `color` 變化（0..1），保留透明度：整個身體以一個剪影閃白受擊 |
| `outline` | 寬度, 強度 | 沿子樹透明度外圍的一圈 `color`（強度 > 1 為 HDR）：超必殺氣場 |

```json
{"name": "front_shoulder", "fx": {"shader": "motionBlur"},
 "tracks": {"fx": [{"t": 0.08, "v": [0, 0, 0, 0]}, {"t": 0.12, "v": [0, 0, 1.4, 0]}, {"t": 0.26, "v": [0, 0, 0, 0]}]},
 "children": [ ... 上臂、手肘、前臂、拳頭 ... ]}
```

- `fx` 關鍵影格控制四個參數，與其他內插通道一樣有緩動。沒有關鍵影格時用靜止的 `params`。
- 看不出效果時**不開圖層**，不花任何成本。包括：模糊向量不到半個像素、程度為 0 的閃白、寬度為 0 的外框，以及隱藏或完全透明的節點。
- 長度隨擺放縮放：以一半大小畫出的片段，模糊與發光也只有一半距離；模糊向量也會跟著擺放旋轉與鏡像。

## 2. 殘影

節點的 `trail` 會畫出 `count` 個子樹的複本，分別是 `gap`、2 × `gap`…… 秒之前的樣子。它們以 `color` 著色：最近的一個透明度為
`color.a`，越舊越淡。殘影畫在節點後面，並在它自己的效果圖層之外。`trail` 關鍵影格（0..1）調整殘影強度；沒有關鍵影格時強度為 1。
`"blend": "add"` 讓殘影發光。

```json
{"name": "body", "trail": {"count": 5, "gap": 0.035, "color": [1, 0.55, 0.15, 0.6], "blend": "add"},
 "tracks": {"trail": [{"t": 0.4, "v": 0}, {"t": 0.48, "v": 1}, {"t": 0.78, "v": 1}, {"t": 0.9, "v": 0}]}}
```

複本是片段在那些較早時間的求值結果（`evaluate`，無狀態），所以跳轉時間後立即正確，循環節點也一樣。

## 3. 檔案：版本 4

`fx`、`trail` 與它們的關鍵影格只在有用到時才寫入，檔案這時標為 `"version": 4`；沒用到的檔案維持版本 2 或 3，舊版程式仍能開啟。
讀檔時會回報錯誤：不認識的著色器、超過 16 個殘影、間隔小於等於 0，或 normal / add 以外的混合方式。

## 4. 實作

| 部分 | 位置 |
|---|---|
| 資料、JSON、`fxParamsAt` / `trailAt`、每個姿勢的子樹範圍 `NodePose::first / end` | `src/core/engine/anim_clip.h/.cpp` |
| 在子樹前後開關圖層、`nodeLayerEffect`、`appendTrail`（`appendDraws` 與 `AnimPlayer::draw` 都有） | `src/core/engine/anim_player.h/.cpp` |
| `IRenderer::beginLayer / endLayer`、`LayerEffect`（預設什麼都不做：沒有圖層的後端照常直接畫出） | `src/core/engine/render_iface.h` |
| 圖層：每層一張 RGBA16F 圖、每層一個 bgfx view、合成 | `src/engine/src/bgfx_renderer.*`、`src/engine/shaders/fs_layer.sc` |
| 編輯器：屬性面板的「效果」區、關鍵影格清單的 Fx 與 Trail 欄 | `tools/anim/qt/AnimPropertiesDock.*`、`AnimKeyListDock.*`、`tools/anim/core/anim_keys.*` |
| 測試 | `unit.anim_fx_test`、`smoke.anim_fx`（超必殺衝刺中）、`anim.check_brawler*` |

繪製器：

- **圖：**每個圖層畫進一張遊戲畫面大小（裝置像素）的 RGBA16F frame buffer，先清成透明。圖是預乘的：圖層內的 sprite
  照常混合顏色，透明度累積覆蓋率；圖再以 (ONE, 1 − alpha) 畫出。
- **View：**每個圖層有自己的 bgfx view（`kViewLayerFirst + n`）。view 順序讓它們在清除畫面後（以及 3D 場景後）、`kViewGame`
  之前執行，**內層先畫**。圖層的圖在它的父 view 中、`beginLayer` 被呼叫的位置畫出，與那裡的四邊形、網格、GPU 粒子交錯。
- **限制：**每格最多 48 個圖層，超過的直接畫出。最上層（`setLayer(1)`，在 UI 之上）不能用圖層。

示範附帶兩項引擎改動：

- **手繪圖集的線性取樣。**頁面寫著 `filter: Linear` 的圖集現在以線性取樣（`IRenderer::setTextureFilter`，由遊戲的資源管理器和
  編輯器設定）。其他圖集仍是點取樣的像素圖，與之前相同。
- 動畫編輯器的 **檢視 > 手持片段**。它把武器檔中同名的片段畫在 `hand` 節點上，與遊戲的 CharacterRig 相同，編輯角色的劍、杖、弓
  攻擊時就能一起看到武器。`anim_editor --render file.anim clip outdir t1,t2,… [held.anim]` 透過遊戲繪製器存出畫格
  （`TOMS_RENDER_ZOOM` 在取景後再放大）。

### 4.1 效能（2026-10-30）

片段如何送到 GPU：

- **批次：**同一張貼圖、同一種混合、其中含有網格的一段四邊形與網格，會合成「一張」網格送出（`DrawList::submit`；每個四邊形
  變成兩個三角形，保留自己的顏色，`Mesh::colors`）。只有四邊形的一段仍是四邊形，由 sprite 批次合併（跨片段也會）。繪製器再把
  相鄰、同貼圖同混合的網格繪製合併（`BgfxRenderer::drawMesh`），一群蒙皮角色只要幾次繪製。
- **蒙皮骨架快取：**每個蒙皮節點與 sprite 保留播放期間不變的資料：區域、貼圖、網格、UV、靜止網格、權重、每根骨頭的姿勢索引與
  靜止變換的反矩陣。每格只需乘骨頭、加權相加。每個片段與圖集組合只有一份快取，所有播放它的 `AnimPlayer` 共用（一群角色只有一份；
  最後一個播放者停止時釋放；重新載入時建立新的）。自動權重也依其來源資料的雜湊保留，所有路徑都適用（編輯器也是）。
- **圖層依內容大小：**圖層的 view、清除與合成只涵蓋它畫的內容加上效果的延伸距離，而非整個畫面。
- **每格不配置記憶體：**殘影與自動動態模糊重用姿勢緩衝；子節點沒有繪製順序時，`evaluate` 也不配置。

以 `toms_game --anim=assets/media/anim/brawler.anim#<片段> --anim-crowd=N --bench --no-vsync` 量測（1600 × 900，Direct3D 11，
本機）：

| 人群 | 繪製次數 | 片段繪製（CPU） | 每格（CPU） | GPU |
|---|---|---|---|---|
| idle × 64，之前 | 705 | 3.1 ms | 4.7 ms | 4.2 ms |
| idle × 64，之後 | 129 | 2.5 ms | 3.8 ms | 3.3 ms |
| super_combo × 16，之前 | 354–692 | 1.4–2.8 ms | 3.9–4.1 ms | 3.8–3.9 ms |
| super_combo × 16，之後 | 116 | 0.5 ms | 1.2 ms | 1.2 ms |

仍在每格進行的：CPU 上的蒙皮、晶格變形的網格（沒有骨架快取：它們的靜止形狀會動）、殘影（它們的蒙皮走完整路徑），以及編輯器的
無狀態路徑（`evaluate` + `appendDraws`）。本機上 100 個格鬥家在 60 fps 的一格內完成（idle 5.9 ms、walk 3.8 ms、super combo 4.1 ms）；
`run`（每個三個殘影、100 個模糊圖層中畫出 48 個）需 15.3 ms；1000 個為 20–30 fps。

**尚未進行的最佳化選項**（擁有者，2026-10-30：留待之後），依效益排序：

| 選項 | 內容 | 時機 |
|---|---|---|
| 殘影使用骨架快取 | 殘影的姿勢順序與片段相同，可直接套用快取 | 許多角色帶殘影奔跑之前 |
| 晶格變形部件的快取 | 保留它們的區域與網格查找（變形本身每格都在動） | 以 idle 為主的人群 |
| 影子獨立一道 | 人群的影子（另一張圖集）夾在身體之間，讓角色無法互相合併繪製 | 人群 |
| **GPU 蒙皮、靜態共用緩衝** | 每張共用網格只上傳一次（靜止位置、UV、骨頭索引與權重）；每個角色只送骨頭矩陣；CPU 不再碰頂點，索引不再複製。骨頭放在所有角色共用的貼圖，保留跨角色的合併繪製 | 大量人群；人群模式的第一步 |
| 人群模式（烘焙動畫貼圖） | 如 glTF 人群（docs/engine/08 §6）：每個片段依節點、依影格烘焙進貼圖，每張圖集頁一次實例化繪製；每個角色只需片段、時間與位置。子樹效果退回一般路徑 | 數百個角色 |
| 翻頁 LOD | 小的或遠的角色用預先算圖的影格（匯出器的離屏算圖，放進圖集）：每個一個四邊形 | 畫面上 1000 個，或效能較弱的裝置 |

### 5.1 美術（ComfyUI）

1. **先固定姿勢。**腳本畫出適合綁骨的 OpenPose 骨架：手臂離開身體、雙腳張開，讓部件盡量不重疊。ControlNet（union promax，
   openpose 模式，全強度）讓 Juggernaut XL 把關節畫在那裡，再用 Inspyrenet 去背。控制較弱時手臂會貼著身體（最初四個種子）；
   最後選了種子 55。
2. **沿同樣的骨頭切出部件。**每個不透明像素歸給最近的骨段。軀幹、頭、骨盆是膠囊形，所以寬闊的胸口留在軀幹上。另有幾條規則切出
   馬尾和紅腰帶的垂尾（依顏色，在沿著它的帶狀範圍內）。
   - **每條肢體一張網格：**上臂與前臂切成一個部件，褲子與靴子也是。第一版把它們當成分開的剛性部件：防禦姿勢時手肘露出切口，
     小腿傾斜時靴子也滑離褲管（擁有者回報，2026-10-30）。拳頭仍是獨立部件，接縫在手套的束帶。
   - **關節重疊：**每個部件只往它的**父部件**延伸 9 像素。子部件畫在父部件上面，所以關節轉動時不會露出縫隙，也不會在別的部件上
     留下多餘的像素。
   - **被遮住的褲子：**被腰帶遮住的褲子用 OpenCV Telea 補畫，並歸給腿，腰帶擺動時腿上不會出現破洞。
   - **乾淨的邊緣：**去背後的柔和邊緣還留著淺色背景的顏色，在部件重疊處成了淡色光暈。不是完全不透明的像素一律改用最近的
     不透明像素的顏色。
3. 部件以一半大小存檔：人物約 565 像素高，是 1080p 畫面上 HD 2D 格鬥角色的大小。

這張圖是面向觀眾、略帶四分之三側身。單一視角的圖無法轉身（見 §6）。

### 5.2 骨架與片段

- **骨頭：**每個關節一個群組節點（腰、頸、馬尾綁結、肩、肘、腕、髖、膝、踝），每個部件的 sprite 放在它的關節上。
- **蒙皮：**每條手臂是一張網格，由肩、肘、腕彎曲；每條腿（褲子加靴子）是一張網格，由髖、膝、踝、腳尖彎曲（docs/engine/16）。
  手肘、膝蓋、腳踝都彎得平順。每張網格是它第一個關節的子節點，所以那裡的效果涵蓋整條肢體。IK 不會讓手臂折超過約 100°
  （手腕離肩至少 95 像素）：再折下去，蒙皮的手肘會擠皺。
- **晶格：**胸口呼吸、腰帶垂尾飄動。
- **產生器裡的 IK：**姿勢以目標寫成（腳或手腕要到哪裡），再由兩骨 IK 解成關節轉角，讓腳穩穩踩在地上。
- **武器：**武器畫在拳頭的 `hand` 節點上，並轉到每個姿勢指定的角度。

| 片段 | 展示內容 |
|---|---|
| idle | 呼吸（軀幹晶格），馬尾與腰帶擺動 |
| walk、run | IK 讓腳踩穩；腿透過蒙皮彎曲。run：身體殘影、前腳動態模糊 |
| punch | 手臂子樹依自己的速度模糊（`motionBlur`，auto）；擊中火花 |
| kick | 整條腿（褲子加靴子）作為一個子樹模糊 |
| hurt | 整個身體以一個剪影閃白（`body` 上的 `flash`） |
| victory | 舉起的拳頭那隻手臂發光（HDR 光暈） |
| super_combo | 畫面變暗；整個身體的外框氣場；帶相加殘影的衝刺；六連擊，每次出手的肢體模糊；火焰上勾拳（肩膀上的 `glow` 圖層**巢狀在**包住它的群組的模糊圖層內，加上 sprite 關鍵影格做的火焰翻頁）；落地爆破 |
| brawler_sword / staff / bow | ready / hold / idle、charge（蓄力時手臂發光）、attack（模糊）、miss、attack_big（外框氣場 + 殘影）；武器由 CharacterRig 畫出 |

重新產生：先 `python tools/art/make_brawler_art.py parts --pick 55`，再
`atlaspack pack Build/art_out/brawler/parts --out assets/media/atlas --name brawler --format atlas --filter Linear --padding 2 --extrude 1`，
然後 `python tools/make_brawler_anim.py` 與 `anim_editor --headless meshes assets/media/anim/brawler.anim`。

## 6. 結論：動畫編輯器做得到而 Spine 做不到的，以及它仍缺少的

**超越 Spine：**

1. **依階層套用著色器：**模糊、HDR 發光、閃白、外框可套在任何子樹上，可巢狀、可設關鍵影格（§1）。Spine 有插槽混合模式和雙色著色，
   但沒有針對骨頭的後製效果。
2. **殘影是節點設定**（§2）。在 Spine 裡要手動複製附件。
3. **網格與權重由工具產生**，來自 sprite 的透明度和骨頭的靜止位置（docs/engine/16）。換新美術風格會重新切網格，動作保持不變。
4. **晶格變形**在重新切網格後仍然有效。Spine 的變形關鍵影格綁死在一張網格上。
5. **武器是獨立檔案**，執行時才綁定（CharacterRig）。

**仍缺少的**（製作示範時發現）：

| 缺少 | 對這次示範的影響 | 可能的解法 |
|---|---|---|
| 編輯器與執行期都沒有 IK | 姿勢是在 Python 產生器裡用 IK 解出來的。在編輯器裡手動做，踩穩的腳要一個關節一個關節去猜 | 節點上的兩骨 IK 約束（像 Spine 的 IK），在 `evaluate` 中求解 |
| 編輯器設關鍵影格是逐節點、逐通道 | 23 個片段由腳本寫出，不是手動做的 | 姿勢庫、鏡像姿勢、跨片段複製姿勢 |
| 單一視角的圖 | 美術面向觀眾；側面的拳腳是正面的圖轉過去。後手出拳時被軀幹擋住 | 多畫幾個視角（側面、背面）用 sprite 關鍵影格切換，或為每個視角畫部件 |
| 沒有繪製順序關鍵影格 | 後手臂一直在軀幹後面 | `order` 關鍵影格軌 |
| 沒有根位移 | 超必殺的衝刺在片段內移動身體，最後再跳回原位 | 遊戲可讀取的「根位移」事件或節點 |
| 部件由一張圖切出 | 重疊處（腰帶蓋住腿）需要補畫；大幅彎曲時會看到切口 | 每個部件分開生成（ComfyUI 逐部件 inpainting） |
| 效果只在遊戲層 | UI 之上畫的 sprite 不能模糊或發光 | 在 `kViewTop` 支援圖層 |
| 只在桌面（D3D11）檢查過 | 圖層需要 RGBA16F 繪製目標（不支援時退回 RGBA8）。尚未在網頁（WebGL2）或 Android 檢查 | 擁有者要求那些版本時再檢查 |

**結論：**對手繪部件的 2D 格鬥遊戲動畫，動畫編輯器加上它的執行期**不需要 Spine 也足夠**，而效果方面更超越 Spine。真正的差距在
製作速度：IK、姿勢工具、繪製順序關鍵影格。這次示範需要腳本來寫出片段。
